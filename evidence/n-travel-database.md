# Supabase 数据库设计

日期：2026-10-14

这一版把账号、城市回忆、照片和行程接到 Supabase。建表语句在 `demo/supabase/schema.sql`。网页不保存服务端密钥，只使用项目 URL 和 anon public key。别人能不能读到某一行，由行级安全策略决定，不由前端自己过滤。

## 表和页面

| 数据库里的东西 | 主键和外键 | 页面上对应什么 |
| --- | --- | --- |
| `auth.users` | Supabase Auth 的用户 id | 注册、登录、退出。密码只留在 Auth 里，业务表不存密码 |
| `cities` | 主键 `id`。`user_id` 指向 `auth.users`，删除账号时城市一起删除。同一用户下「城市 + 国家」唯一 | 地图上的点，城市页那一段感受 |
| `photos` | 主键 `id`。`user_id` 指向用户，`city_id` 指向 `cities`。同一用户下文件哈希唯一 | 上传核对、城市页的照片。点进城市，就是按 `city_id` 取出这些行 |
| `trips` | 主键 `id`。`user_id` 指向用户。`from_city_id` 和 `to_city_id` 都指向 `cities`，数据库里的名字是 `trips_from_city_fkey`、`trips_to_city_fkey` | 行程列表和地球上的弧线。两端城市必须先存在，所以弧线的两端一定是已经点亮、可以写感受的城市 |
| Storage 桶 `photos` | 路径是 `用户id/照片id`。策略只允许登录用户读写自己的文件夹 | 城市页的图片。表里的 `storage_path` 指向这个文件 |

## 为什么这样拆

一座城市只有一段感受，再去只追加照片。所以感受放在 `cities`，用「用户 + 城市 + 国家」做唯一约束，而不是每张照片写一句。

照片必须归到某座城市，上传页在保存前就要选定城市。`photos.city_id` 用外键保证不会出现一座数据库里不存在的城市。城市名字不抄到照片行上，打开照片时向 `cities` 取名字，避免行程端和照片端各写一遍、以后改名对不上。

行程的价值是把两座已有城市连起来。两条外键让「上海 → Schweiz」必须指向两行城市，地图才知道弧线的坐标，城市页才能接着写感受。

每张业务表都有 `user_id`，策略是 `auth.uid() = user_id`。地图、上传、城市、行程读到的都是当前登录用户的行。这和页面上「退出后另一个邮箱看不到这些内容」是同一件事。

照片原文件放到 Storage，单张上限 15MB，和上传页的限制一致。`photos` 只存路径、拍摄时间、坐标和哈希。哈希的唯一约束对应「这张已经在你的地图里」。

`feeling` 最长 1000 字，和城市页、上传页的输入框一致。`trips.kind` 只允许 `flight` 和 `train`，对应机票和火车票两个选项。
